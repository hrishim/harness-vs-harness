Test setup

Everything below is what the runs in this report actually used. Dates are 8 to 10 November 2026.

Model and server
Model Alibaba Qwen3.8-Flash-Next, NVIDIA's NVFP4 quantisation (nvidia/Qwen3.8-Flash-Next-NVFP4 on Hugging Face; ModelOpt mixed precision: NVFP4 weights, FP8 for some layers), snapshot fc694b54fb0174e0913e6adf86691ef85a4ead47. Served as qwen3.8-flash-nvfp4
Machine NVIDIA DGX Spark (GB10), driver 580.178.04, Linux 7.0.0-1019-nvidia
Recipe Setup D (our own speed trial): the published salient-data/qwen38-next-dgx Docker image, pinned by digest sha256:3d67df7b7b7d25a5da64f62c0f87f6109062584261fe77157f6d37de178d10b2, launched as the recipe repository salient-data/qwen38-next-dgx-recipe (version f309019, 15 Oct 2026) prints it, with our household settings (model name, tool parser, 8 requests at once, thinking on)
Engine vLLM 0.32.0rc1.dev100+g77154ca61 (nightly build 77154ca6), PyTorch 2.13.0+cu130, transformers 5.19.0
Front end llama-swap v255 (7761aa1) on port 4000, concurrency limit 8. It removes max_tokens from every request, so no harness has an output cap
Context window 262,144 tokens
One user at a time The runs were executed one after another; the server never served two runs at once

Defaults when a harness sends nothing (from the model's chat template and config): thinking is on; reasoning effort is xhigh (the template accepts xhigh, medium or low); sampling is temperature 1.0, top-k 20, top-p 0.95. None of the five harnesses sent its own sampling settings.

Test environment

  • 15 tests, 3 rounds each per harness, so 45 runs per harness. Prompts are one-shot and written as a person would ask (see the Tests page); every input file is invented for the test.
  • A fresh Docker container per run, from a shared base image (Ubuntu 24.04.5, Python 3.12.3, Node 22.23.4, GnuCash 5.5 with the SQLite backend, Poppler, pypdf, PyMuPDF, ReportLab, piecash, icalendar, Playwright with Chromium, exiftool, Tesseract). It sees only the task's input/ folder and the prompt. Memory limit 6 GB, time limit 45 minutes.
  • Isolated network. The container's only neighbour is a gateway container with two parts: a recording proxy to the model server (it records every request's token counts, cache hits, timings and tool calls) and a web proxy (internet allowed; private network addresses refused).
  • Scoring is rule-based, with no AI judge: file contents, PDF form fields and pixels, hidden unit tests, browser tests and fact checks. Each check is a percentage per category; the score is the average, so 100% means fully correct. Each check is tested against known-correct and known-wrong answers before it is used.
  • Efficiency comes from the recording proxy. Real tokens = the new text the model had to read plus everything it wrote (see the top of this page); time, turns and tool calls are counted per run.
  • Runs that had to be redone. 44 runs were set aside and run again because something went wrong with the run itself, not with the model's work: 5 Hermes runs where a model reply never arrived and Hermes was stopped, 2 Hermes runs and 1 DeepSeek run that never started, 23 OpenCode runs where my first setup blocked access to files outside the task folder, 4 Hermes runs that finished with trouble, and 9 runs (5 OpenCode, 2 DeepSeek, 1 Hermes, 1 Claude Code) during which the laptop running the tests went to sleep, which paused the test containers and inflated their times; the scores were the same in 7 of the 9. The Data page lists them and the runs that hit the 45-minute limit.
